ספרינט 2: סכמות ו-seed, וסרבר א'

איך מתחילות לעבוד בשרת: איך יודעות אילו אוספים לבנות ואילו שדות יש בהם, איפה בונות אותם, ואיזה כללים שומרים.

מסלול א': השבוע רק חלק א' (סכמות ו-seed). מי שלא סיימה את הקליינט מסיימת אותו קודם. סרבר א' בשבוע הבא.
מסלול ב': חלק א' עד יום ראשון, ב-PR קטן. מיום שני חלק ב' (סרבר א').

המורה מודיעה בכיתה באיזה מסלול השבוע. בשני המסלולים מתחילים מחלק א'.

לפני שמתחילות (פעם אחת)

  1. MongoDB רץ על המחשב. מתקינות MongoDB Community Server גרסה 7.0 ל-Windows (הורדה), עם ברירות המחדל ועם הסימון "Install MongoD as a Service". חלופות: Docker (docker compose up -d), או MongoDB Atlas בענן.
  2. השרת רץ: בתיקייה school-server מריצות npm install, cp .env.example .env, npm run seed ו-npm run dev.
  3. רואות את הנתונים: מתקינות ב-VS Code את התוסף MongoDB for VS Code, לוחצות על העלה הירוק, ואז Add Connection ומדביקות mongodb://localhost:27017. בחלונית CONNECTIONS פותחות school ואוסף.
  4. פותחות את החוזה כ-Swagger: מתקינות ב-VS Code את התוסף OpenAPI (Swagger) Editor, ופותחות את school-server/openapi/openapi.yaml. לוחצות בתוך הקובץ ואז Shift+Alt+P (או Ctrl+Shift+P ובוחרות OpenAPI: show preview). נפתח לצד הקובץ עמוד עם כל ה-endpoints, ולמטה, תחת Schemas, כל הסכמות. בפעם הראשונה בוחרות Swagger UI. הסרגל השמאלי של התוסף (סמל OpenAPI) מציג עץ של Paths ו-Schemas.
  5. קוראות את מודול ההדרכה src/modules/announcements בשרת. הוא מראה את כל הדפוס: מודל, seed, routes ובדיקות.

הרצת seed ולא רואה נתונים? ייתכן שאצלך רצים שני שרתי MongoDB (גם התקנה ב-Windows וגם Docker), ואת מסתכלת על השרת השני. בחרי אחד מהם ועצרי את האחר.

מה זה סכמה ומה זה seed

מושגמה זה
סכמה (מודל)החוקים של אוסף: אילו שדות, מאיזה סוג, מה חובה ומה ייחודי. נכתבת בקוד, ב-model.ts, ו-Mongoose בודק לפיה כל רשומה לפני שהוא שומר אותה.
seedקוד שממלא את המסד בנתוני דוגמה קבועים, כדי שהמסך יציג נתונים כבר בהרצה הראשונה, וכל הצוות יראה את אותם נתונים.
אוסף ליבהinstitutions, academic_years, users, roles, staff_profiles, classes, students, subjects. מוכנים מראש ב-src/models.
אוסף משותףאוסף שכמה מסכים קוראים ממנו: rooms, events, teaching_assignments, lessons, invites, assessments, grades, grade_feedback, attendance_records ו-attendance_alerts. גם הם כבר מוכנים ב-src/models, ולכן אף אחת לא מחכה לאחרת.

שלב 1: מה את בונה

פותחות את עמוד המסך באפיון (אינדקס המסכים) ויורדות לסעיף "שרת ונתונים". שם כתוב בדיוק מה בונים בכל שלב:

מה כתוב שםמה עושות
"בונות: המודל ...", עם טבלת שדותאוסף פרטי של המסך שלך. בונות לו מודל ו-seed במודול שלך
"אוספים שמייבאים (לא בונים)"אוספי ליבה ומשותפים. לא בונות אותם, רק מייבאות מ-src/models. שורת ה-import כבר כתובה בעמוד
"המסך הזה כותב אליו בסרבר ב'"אוסף משותף שהמסך שלך אחראי על ה-endpoints שכותבים אליו. המודל קיים, ואת הכתיבה בונים בספרינט 3

אין במסך שלך אוסף "בונות"? זה המצב אצל עשר מפתחות, וזה בסדר. בשלב הזה בודקות שהמודלים בליבה מספיקים למסך, ושיש ב-seed נתונים לכל מצב שלו (רשימה מלאה, ריקה, ערך חסר). חסר שדה או נתון? לא משנות את הליבה: כותבות לראשת הצוות ב-Slack.

מאיפה באים השדות

בעמוד המסך יש טבלת שדות לכל אוסף שבונות, וזה המודל שבונים. השדות נגזרו מהאפיון של המסך. כך גוזרים שדות בכל פרויקט, וכדאי להבין את זה גם כשהטבלה כבר מוכנה:

מה כתוב ב-SPECמה זה אומר על המודל
שדה בטופס עם * ("תיאור *")שדה חובה (required: true)
שדה בטופס בלי כוכביתשדה רשות. אם הוא יכול להיות ריק: default: null
עמודה בטבלה ("נכתב ע"י")שדה שהשרת מחזיר. לפעמים זה מזהה (authorId), והשם מגיע מהאוסף שאליו הוא מפנה
רשימת אפשרויות ("סוג: חיובי, משמעת, אחר")enum עם ערכים באנגלית: ['positive', 'discipline', 'other']
כלל: "אסור ש..." / "רק אחד..."אינדקס ייחודי, או בדיקה בשרת
כלל: "מחיקה רכה"שדה deletedAt במקום מחיקה אמיתית

גם התגובה של ה-API כבר מוגדרת בחוזה, בסכמה עם שם המודל. חסר שדה? כותבות לראשת הצוות. ב-endpoints שמרכזים נתונים (דשבורד, דוח, חיפוש) מסומן טרם הוגדרה: שם בעלת המסך כותבת את מבנה התגובה ב-openapi.yaml באותו PR של ה-route, וראשת הצוות רואה אותו בקוד ריוויו.

שלב 3: המודל (model.ts)

import { Schema, model, type InferSchemaType } from 'mongoose';
import { DATE_ONLY } from '../../utils/dateOnly';

const fooSchema = new Schema(
  {
    institutionId: { type: Schema.Types.ObjectId, ref: 'Institution', required: true, index: true }, // 1
    barId: { type: Schema.Types.ObjectId, ref: 'Student', required: true },                         // 2
    name: { type: String, required: true, trim: true },
    status: { type: String, enum: ['open', 'closed'], default: 'open' },                             // 3
    day: { type: String, required: true, match: DATE_ONLY },                                         // 4
    note: { type: String, trim: true, default: null },                                               // 5
  },
  { timestamps: true, collection: 'foos' },                                                          // 6
);
fooSchema.index({ institutionId: 1, name: 1 }, { unique: true });                                    // 7

export type FooDoc = InferSchemaType<typeof fooSchema>;
export const Foo = model('Foo', fooSchema);
  1. 1. כל אוסף שייך למוסד, עם אינדקס.
  2. 2. הפניה לאוסף אחר: ObjectId עם ref לשם המודל ('Student', 'SchoolClass'), לא לשם האוסף.
  3. 3. רשימה סגורה של ערכים: enum, בדיוק כמו בחוזה.
  4. 4. תאריך בלי שעה: מחרוזת 'YYYY-MM-DD'.
  5. 5. שדה שיכול להיות ריק: default: null.
  6. 6. createdAt ו-updatedAt נוספים לבד.
  7. 7. מה שאסור שיחזור פעמיים: אינדקס ייחודי.

דוגמאות אמיתיות בשרת: src/models/room.model.ts (פשוטה), ו-src/models/attendanceRecord.model.ts (תאריך, null ואינדקס ייחודי על כמה שדות).

שלב 4: ה-seed (seed.ts)

import { Institution, Student } from '../../models';
import { Foo } from './model';

/** Demo data for the screen. Idempotent: running it twice changes nothing. */
export async function seed(): Promise<void> {
  const inst = await Institution.findOne({ name: 'בית ספר לדוגמה' });
  if (!inst) return;
  const students = await Student.find({ institutionId: inst._id }).sort({ nationalId: 1 }).limit(2);
  const items = [
    { name: 'foo', status: 'open', day: '2026-10-20' },
    { name: 'bar', status: 'closed', day: '2026-10-21' },
  ];
  for (let i = 0; i < items.length; i++) {
    await Foo.updateOne(
      { institutionId: inst._id, name: items[i].name }, // the natural key
      { $set: { ...items[i], institutionId: inst._id, barId: students[i]._id } },
      { upsert: true },
    );
  }
}

ה-seed של המודול רץ לבד ב-npm run seed, אחרי ה-seed של הליבה ושל האוספים המשותפים, ולכן מותר לו לקרוא מכל מה שב-src/models.

חלק ב': סרבר א' (endpoints לקריאה)

מתחילות רק אחרי שה-PR של חלק א' מוזג: במסלול ב' מיום שני, ובמסלול א' בשבוע הבא.

  1. 1. מוצאות את ה-GET שלך: בעמוד המסך, בטבלה "ה-endpoints בחוזה", בשורות שהשלב שלהן הוא "סרבר א'".
  2. 2. כותבות את ה-route ב-routes.ts (התבנית כבר שם): authorize('<מסך>', 'read') בראש כל route, סינון לפי institutionId: req.user!.institutionId, ועימוד עם parsePagination ו-toPage כשהתגובה בחוזה היא ...Page.
  3. 3. ממפות לצורה שבחוזה: id: String(doc._id), ובלי שדות פנימיים כמו institutionId או __v.
  4. 4. בודקות: לפחות בדיקה אחת לכל endpoint (בלי טוקן מקבלים 401, ועם טוקן מקבלים את מבנה החוזה), ובדיקה ידנית עם curl.

"מוגבלת לשלו" בטבלת ההרשאות בעמוד המסך: מסננים לפי הכיתות, המקצועות או הילדים של המשתמש, עם services/scope.ts. את הכתיבה (POST, PUT ו-DELETE) ואת הולידציה בונים בסרבר ב', בספרינט 3.

  • ה-endpoints זהים לחוזה: נתיב, פרמטרים ומבנה התגובה
  • עימוד, מיון וסינון לפי החוזה
  • בדיקת הרשאה וסינון לפי מוסד
  • בדיקה לכל endpoint, ו-npm run verify ירוק
